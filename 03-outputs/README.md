# Terraform Fundamentals — 03 Outputs

This lab explores **Terraform output values** and how Terraform exposes values from resources, variables, and expressions.

The previous lab (`02-variables`) focused on providing input to Terraform through variables. This lab focuses on the opposite direction: **exposing values from Terraform configuration and state**.

---

## Objectives

In this lab, we learned:

- What Terraform outputs are
- How to expose resource attributes
- How to expose variable values
- How to create outputs from expressions
- How outputs are stored in Terraform state
- How to retrieve outputs with `terraform output`
- The difference between normal output and `-raw`
- Machine-readable output with `-json`
- How Terraform handles complex output types
- Sensitive outputs
- How output changes can occur without infrastructure changes
- How Terraform automatically understands dependencies through references

# 1. Basic Output

An output block exposes a value from the root Terraform module.

Example:

```hcl
output "file_name" {
  value = local_file.hello.filename
}
```

The output references the `filename` attribute of the `local_file` resource.

The dependency is automatically understood by Terraform because the output references the resource.

---

# 2. Output From a Resource Attribute

The `content` output exposes the content of the generated file:

```hcl
output "content" {
  value = local_file.hello.content
}
```

The dependency is:

```text
local_file.hello
       │
       └── content
             │
             ▼
          output
```

Terraform does not require an explicit dependency declaration for this relationship.

---

# 3. Output From a Resource Attribute That Terraform Calculates

The `local_file` resource exposes several calculated attributes.

For example:

```hcl
output "content_md5" {
  value = local_file.hello.content_md5
}
```

After applying the configuration:

```powershell
terraform output content_md5
```

returns the stored MD5 value.

This demonstrates that outputs can expose values calculated by providers.

---

# 4. Output From a Variable

An output does not have to reference a resource.

Example:

```hcl
output "configured_message" {
  value = var.message
}
```

The value flows directly from the input variable:

```text
var.message
     │
     ▼
configured_message
```

This is different from:

```hcl
output "content" {
  value = local_file.hello.content
}
```

where the value comes from the resource.

An output can therefore expose the result of **any valid Terraform expression**, not just a resource attribute.

---

# 5. Output From an Expression

Outputs can also contain expressions combining values.

Example:

```hcl
output "file_summary" {
  value = "${local_file.hello.filename} contains the configured message."
}
```

Terraform evaluates the expression and stores the resulting value:

```text
hello.txt contains the configured message.
```

The dependency on `local_file.hello.filename` is automatically understood.

---

# 6. Outputs and Terraform State

Outputs are stored in Terraform state after `terraform apply`.

For example:

```powershell
terraform output
```

reads the stored root-module outputs from state.

Adding an output does not necessarily change infrastructure.

For example, adding:

```hcl
output "configured_message" {
  value = var.message
}
```

can produce a plan containing:

```text
Changes to Outputs:
+ configured_message = "Hello from Terraform Outputs!"
```

while the infrastructure itself remains unchanged.

This is an important distinction:

```text
Terraform configuration change
          │
          ├── Infrastructure change
          │
          └── State/output change
```

`terraform apply` synchronizes Terraform's state with the configuration. It does not necessarily mean that a real infrastructure resource will be created, modified, or destroyed.

---

# 7. `terraform output`

Running:

```powershell
terraform output
```

displays all root-module outputs.

A specific output can also be requested:

```powershell
terraform output file_name
```

For example:

```text
"hello.txt"
```

Normal output uses Terraform's human-readable representation.

---

# 8. `terraform output -raw`

The `-raw` option returns a single scalar output without Terraform's normal display formatting.

Example:

```powershell
terraform output -raw content
```

returns:

```text
Files configured: hello.txt? world.txt!
Hello from Terraform Outputs!
```

Instead of the normally formatted:

```text
"Files configured: hello.txt? world.txt!
Hello from Terraform Outputs!"
```

`-raw` requires the name of one output:

```powershell
terraform output -raw
```

produces:

```text
Error: Output name required
```

It is intended for scalar values and is particularly useful when passing Terraform output directly into shell commands, scripts, or CI/CD workflows.

---

# 9. `-raw` and Complex Types

The `-raw` option does not support complex Terraform values.

For example:

```hcl
output "file_names" {
  value = ["hello.txt", "world.txt"]
}
```

Running:

```powershell
terraform output file_names
```

produces:

```text
tolist([
  "hello.txt",
  "world.txt",
])
```

But:

```powershell
terraform output -raw file_names
```

produces an error similar to:

```text
Error: Unsupported value for raw output

The -raw option only supports strings, numbers, and boolean values,
but output value "file_names" is list of string.
```

Therefore:

```text
string / number / boolean
        ↓
       -raw
```

while:

```text
list / map / object / other complex values
        ↓
       -json
```

---

# 10. Why `tolist(...)` Appears

The output:

```text
tolist([
  "hello.txt",
  "world.txt",
])
```

is Terraform's representation of a list value.

The original expression:

```hcl
["hello.txt", "world.txt"]
```

is initially interpreted as a tuple literal.

Terraform evaluates the expression and determines that the resulting collection is a list of strings.

Conceptually:

```text
["hello.txt", "world.txt"]
          │
          ▼
      list(string)
          │
          ▼
terraform output
          │
          ▼
tolist([...])
```

This connects to the collection and type concepts explored in `02-variables`.

# 11. JSON Output

Terraform can return all outputs as machine-readable JSON:

```powershell
terraform output -json
```

The output contains metadata as well as the actual value.

Example:

```json
{
  "file_name": {
    "sensitive": false,
    "type": "string",
    "value": "hello.txt"
  }
}
```

The structure contains:

```text
output name
├── sensitive
├── type
└── value
```

This makes `-json` useful when another program, script, or CI/CD pipeline needs to consume Terraform outputs.

---

# 12. Raw vs Normal vs JSON

The three forms can be viewed as:

```text
terraform output
        │
        ▼
Human-readable Terraform output


terraform output -raw <name>
        │
        ▼
Single scalar value
        │
        ▼
Shell / scripts / CI


terraform output -json
        │
        ▼
Structured machine-readable data
        │
        ▼
Programs / automation / CI/CD
```

# 13. Sensitive Outputs

Terraform supports marking an output as sensitive:

```hcl
output "demo_secret" {
  value     = "this-is-a-demo-secret"
  sensitive = true
}
```

Terraform then masks the value in normal CLI output.

For example, the plan displays:

```text
demo_secret = (sensitive value)
```

and after applying:

```text
demo_secret = <sensitive>
```

The actual value is still known to Terraform.

---

# 14. Sensitive Does Not Mean Encrypted

An important observation from this experiment is that:

```hcl
sensitive = true
```

does **not** mean that the value is encrypted or removed from Terraform state.

The value remains available to Terraform.

For example, `terraform output -json` returned:

```json
"demo_secret": {
  "sensitive": true,
  "type": "string",
  "value": "this-is-a-demo-secret"
}
```

This demonstrates that `sensitive` primarily controls how Terraform displays the value in normal output.

It should therefore not be treated as an access-control mechanism.

---

# 15. Sensitive Values and Azure

`sensitive` is a Terraform feature, not an Azure-specific feature.

It can be used with values originating from:

- Azure resources
- Azure data sources
- Terraform variables
- Terraform modules
- Resource attributes
- Expressions

For example, a Terraform configuration could expose a sensitive Azure value through:

```hcl
output "database_password" {
  value     = azurerm_mssql_server.example.administrator_password
  sensitive = true
}
```

The `sensitive` attribute belongs to the Terraform `output` block.

The Azure resource itself does not need to provide a Terraform `sensitive` argument for the output block to use it.

# Key Takeaways

### 1. Outputs expose Terraform values

```hcl
output "name" {
  value = ...
}
```

The value can come from a resource, variable, data source, module, or expression.

### 2. Outputs are stored in state

After `terraform apply`, root-module outputs become available through:

```powershell
terraform output
```

### 3. Outputs do not necessarily represent infrastructure changes

An output can change while:

```text
Resources added     = 0
Resources changed   = 0
Resources destroyed = 0
```

### 4. `-raw` is for scalar values

```powershell
terraform output -raw <name>
```

supports strings, numbers, and booleans.

### 5. `-json` is for structured consumption

```powershell
terraform output -json
```

is appropriate when another tool or script needs structured Terraform output.

### 6. Complex types are not raw values

Lists, maps, and objects require structured representation rather than `-raw`.

### 7. Sensitive outputs are masked in normal CLI output

```hcl
sensitive = true
```

protects against accidental display but does not itself encrypt the value or remove it from state.

### 8. Terraform automatically understands dependencies

Referencing:

```hcl
local_file.hello.filename
```

inside an output establishes the relationship automatically.
