## Terraform Configuration

The resource uses variables for both the filename and file content:

```hcl
resource "local_file" "hello" {
  filename = var.file_name
  content  = "Files configured: ${join("? ", var.file_names)}!\n${var.message}"
}
```

The generated file therefore demonstrates multiple variables being evaluated together.

Example output:

```text
Files configured: app.txt? config.txt? data.txt!
Hello from terraform.tfvars!
```

# Input Variables

Variables are declared using the `variable` block.

Example:

```hcl
variable "message" {
  type    = string
  default = "Hello from Terraform Variables!"
}
```

A variable can then be referenced using:

```hcl
var.message
```

---

## Variable Without a Default

When a variable has no default value:

```hcl
variable "message" {
  type = string
}
```

Terraform asks for the value when running a command such as:

```powershell
terraform plan
```

Example:

```text
var.message
  Enter a value:
```

This demonstrates that variables can be required inputs.

---

## Variable Defaults

Adding a default:

```hcl
variable "message" {
  type    = string
  default = "Hello from Terraform Variables!"
}
```

means Terraform can use the default value without prompting for input.

---

# CLI Variable Override

A variable can be overridden from the command line:

```powershell
terraform plan -var="message=Hello Architect"
```

The CLI value takes precedence over the default value.

---

# terraform.tfvars

Terraform automatically loads values from `terraform.tfvars`.

Example:

```hcl
message   = "Hello from terraform.tfvars!"
file_name = "hello.txt"

file_names = ["app.txt", "config.txt", "data.txt"]

tags = {
  environment = "lab"
  application = "terraform-fundamentals"
  owner       = "boss"
}
```

This allows variable values to be separated from the Terraform configuration.

---

# Variable Precedence

During the experiments in this lab, we observed the following precedence:

```text
-var
  ↓
terraform.tfvars
  ↓
default
```

A value supplied using `-var` overrides the value in `terraform.tfvars`, which overrides the variable's default.

Terraform has additional variable input mechanisms that will be explored separately when needed.

# Variable Types

Terraform variables can have type constraints.

Examples:

```hcl
type = string
```

```hcl
type = number
```

```hcl
type = bool
```

```hcl
type = list(string)
```

```hcl
type = map(string)
```

```hcl
type = set(string)
```

Type constraints allow Terraform to validate and, where possible, convert supplied values to the expected type.

---

# Type Conversion

Terraform can automatically convert some primitive values when a variable has a type constraint.

For example, with:

```hcl
variable "file_name" {
  type = string
}
```

the following values were accepted:

```hcl
file_name = 10
```

which became:

```text
"10"
```

and:

```hcl
file_name = true
```

which became:

```text
"true"
```

However, supplying a collection such as:

```hcl
file_name = ["hello.txt"]
```

does not turn the collection into a scalar string.

The important lesson is that Terraform performs type conversion where the types are compatible; it does not arbitrarily convert any value into any other type.

---

# Lists

A list contains elements of the same type.

Example:

```hcl
variable "file_names" {
  type    = list(string)
  default = ["hello.txt", "world.txt"]
}
```

Our `terraform.tfvars` contains:

```hcl
file_names = ["app.txt", "config.txt", "data.txt"]
```

The list can be accessed by index:

```hcl
var.file_names[0]
```

Result:

```text
"app.txt"
```

```hcl
var.file_names[2]
```

Result:

```text
"data.txt"
```

Terraform uses zero-based indexing.

Trying to access:

```hcl
var.file_names[3]
```

produces an invalid index error because the list contains only three elements.

---

## List Length

The number of elements can be obtained with:

```hcl
length(var.file_names)
```

Result:

```text
3
```

The last element can therefore be accessed without hard-coding the index:

```hcl
var.file_names[length(var.file_names) - 1]
```

Result:

```text
"data.txt"
```

---

# Tuple vs List

Terraform distinguishes between tuples and lists.

A literal such as:

```hcl
["app.txt", "config.txt", "data.txt"]
```

is initially interpreted as a tuple.

We verified this with:

```hcl
type(["app.txt", "config.txt", "data.txt"])
```

which produced:

```text
tuple([string, string, string])
```

A tuple can contain elements of different types:

```hcl
["app.txt", 10, true]
```

produces:

```text
tuple([string, number, bool])
```

A list, on the other hand, is homogeneous:

```hcl
list(string)
```

All elements must ultimately be strings.

`tolist()` can convert a compatible collection into a list:

```hcl
tolist(["app.txt", "config.txt", "data.txt"])
```

---

# join()

`join()` converts a list of strings into a single string using a separator.

Example:

```hcl
join("? ", var.file_names)
```

Given:

```text
["app.txt", "config.txt", "data.txt"]
```

the result is:

```text
"app.txt? config.txt? data.txt"
```

The transformation is:

```text
list(string)
      ↓
    join()
      ↓
string
```

`join()` does not modify the original variable. It produces a new string.

---

# Maps

A map stores values using keys.

Example:

```hcl
variable "tags" {
  type = map(string)

  default = {
    environment = "dev"
    application = "web"
    owner       = "terraform"
  }
}
```

The values supplied through `terraform.tfvars` are:

```hcl
tags = {
  environment = "lab"
  application = "terraform-fundamentals"
  owner       = "boss"
}
```

A value can be accessed using its key:

```hcl
var.tags["environment"]
```

Result:

```text
"lab"
```

---

# lookup()

Direct access:

```hcl
var.tags["region"]
```

produces an error if the key does not exist.

`lookup()` can provide a fallback:

```hcl
lookup(var.tags, "region", "unknown")
```

Result:

```text
"unknown"
```

For an existing key:

```hcl
lookup(var.tags, "environment", "unknown")
```

Result:

```text
"lab"
```

This makes `lookup()` useful when a key may not exist.

---

# Map vs Object

Terraform also has the `object` type.

An object has a known structure with defined attributes and types.

For example:

```hcl
{
  environment = "dev"
  application = "web"
  owner       = "terraform"
}
```

was identified as:

```text
object({
  application: string,
  environment: string,
  owner: string,
})
```

A `map(string)` instead represents an arbitrary collection of keys whose values are strings.

Conceptually:

```text
object
  → known attributes and structure

map(string)
  → arbitrary keys
  → all values are strings
```

---

# Sets

A set contains unique values and does not provide index-based access.

Example:

```hcl
toset(["app.txt", "config.txt", "app.txt"])
```

produces:

```text
toset([
  "app.txt",
  "config.txt",
])
```

The duplicate value is removed.

---

## Sets Do Not Have Indexes

This does not work:

```hcl
toset(["z", "a", "m", "b"])[0]
```

Terraform reports that elements of a set are identified by their values rather than by indexes.

A set should therefore be treated as a collection where **membership matters, not position**.

---

## contains()

Membership can be checked using:

```hcl
contains(toset(["z", "a", "m", "b"]), "a")
```

Result:

```text
true
```

A value that is not present returns:

```text
false
```

Types also matter:

```hcl
contains(toset(["z", "a", "m", "2"]), "2")
```

returns:

```text
true
```

while:

```hcl
contains(toset(["z", "a", "m", "2"]), 2)
```

returns:

```text
false
```

The string `"2"` and the number `2` are different values.

# Inspecting Types

Terraform's `type()` function was useful throughout this lab.

Examples:

```hcl
type(var.file_names)
```

```text
list(string)
```

```hcl
type(var.tags)
```

```text
map(string)
```

```hcl
type(join("? ", var.file_names))
```

```text
string
```

Using `type()` is a useful debugging technique when Terraform behaves differently from what is expected.

# Key Takeaways

The main lessons from this lab are:

1. Variables allow configuration values to be separated from resource definitions.
2. Variables can have defaults or require external input.
3. `terraform.tfvars` can provide variable values automatically.
4. CLI values can override values from `terraform.tfvars`.
5. Type constraints help Terraform validate variable values.
6. Terraform can perform some automatic type conversions.
7. Lists are ordered collections and support indexing.
8. Tuples describe positional collections and can contain different types.
9. Maps provide key/value access.
10. Objects describe a known structure of attributes.
11. Sets contain unique values and do not support index-based access.
12. `join()` converts a list of strings into a single string.
13. `lookup()` can provide a fallback when a map key is missing.
14. `contains()` can test membership in a collection.
15. `type()` is useful when investigating Terraform's type system.
